# План A/B-тестирования моделей кредитного скоринга
Задача: сравнить две версии модели прогноза дефолта по кредитным картам и принять решение о замене контрольной модели.

| Группа | `model_version` | Модель | Файл артефакта |
|--------|-----------------|--------|----------------|
| A (контроль) | `v1` | Logistic Regression | `models/logistic_regression_model.pkl` |
| B (тест) | `v2` | Random Forest | `models/random_forest_model.pkl` |

Обе модели используют один `models/preprocessor.pkl` (`OneHotEncoder` + `StandardScaler`).

Гипотеза: `v2` улучшает качество скоринга (F1 и/или бизнес-метрики) без роста пропущенных дефолтов относительно `v1`.

Primary metric: F1-score для класса дефолта (`1`).

Secondary metrics: Recall (класс 1), Precision (класс 1).


Для этого было реализовано:
- загрузка `v1`, `v2` и препроцессора при старте;
- автосплит при `AB_TEST_ENABLED=true`: SHA-256 от `customer_id` → стабильная группа;
- ручной override: поле `model_version` в JSON (`ab_assigned: false`);
- поля ответа: `model_version`, `ab_assigned`, `ab_group` (`A` = v1, `B` = v2);
- JSON-логи в stdout для последующего анализа;
- Docker Compose: `AB_TEST_ENABLED=true`, `AB_SPLIT_RATIO=0.5`.

Доступные аеременные окружения для управления тестом

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `AB_TEST_ENABLED` | `false` (локально), `true` (Compose) | Включить автосплит |
| `AB_SPLIT_RATIO` | `0.5` | Доля трафика на `v2` |
| `AB_HASH_FIELD` | `customer_id` | Поле для бакета (fallback: `request_id`, `ID`) |

### Дизайн эксперимента

- Клиент (`customer_id` или `ID` из датасета), не отдельный HTTP-запрос. Иначе один заёмщик может попасть и в A, и в B.
- Основной путь (в сервисе): не передавать `model_version`, обязательно передать `customer_id`.
- Управление трафиком через переменные окружения

так получаем честную радомизацию эксперимента.


```python
# app/ab_split.py  детерминированный бакет
bucket = int(sha256(customer_id)[:8], 16) % 100
v2 if bucket < int(AB_SPLIT_RATIO * 100) else v1
```

Альтернативы:

- API Gateway выставляет `model_version` до ML-сервиса;
- канареечный трафик: явный `model_version` для отладки (5–10%).

#### Длительность и объём

| Параметр | Рекомендация                                           |
|----------|--------------------------------------------------------|
| Календарный период | 2–4 недели                                             |
| Минимум наблюдений | ≥ 10к заявок с известным исходом на группу (при 50/50) |
| Досрочная остановка | только по guardrails                                   |

UCI (~30 000 записей) подходит для офлайн-симуляции, онлайн A/B требует реальных исходов после решений по скору.

#### Порог решения τ

- `probability ≥ τ` → отказ / высокий риск;
- `probability < τ` → одобрение.

τ фиксируется до старта и одинаков для групп A и B.

## Метрики

### ML-метрики (основные)

Расчёт отдельно для A и B при известной `actual_default`:

| Метрика | Роль | Обоснование |
|---------|------|-------------|
| F1 (класс 1) | Primary | Баланс precision и recall по дефолту |
| Recall (класс 1) | Secondary | Минимизация пропущенных дефолтов (FN) |
| Precision (класс 1) | Secondary | Контроль ложных тревог (FP) |
| ROC-AUC | Дополнительно | Качество ранжирования при разных τ |
| Confusion matrix | Аудит | FN, FP, TN, TP |

Выбор Recall как secondary: в кредитном скоринге стоимость FN (пропущенный дефолт) обычно выше стоимости FP.

### Бизнес-метрики 

1. Ожидаемые потери от FN

   `Loss_FN = FN × Avg_Default_Loss`

   `Avg_Default_Loss`  средний убыток на дефолтного клиента (лимит × LGD или фактический остаток).

2. Доля одобрений при фиксированном риске

   При том же τ сравнить:
   - `% approved = (TP + FP) / N` или долю одобренных заявок;
   - default rate среди одобренных.

   Цель B: больше одобрений при не большем дефолте среди одобренных.

3. Cost_FP = FP × Opportunity_Cost  упущенная маржа.

## Статистический анализ

### Сравнение долей (Precision, Recall, approval rate)

- Z-test для двух пропорций или χ² на таблице 2×2 (при больших n).

### Доверительные интервалы

- 95% CI для разницы метрик (F1, Recall, business loss);
- если CI для разницы F1 не включает 0 → эффект значим на уровне α = 0.05 (при одной primary-метрике).

### Непрерывные величины

- Bootstrap по `customer_id` (предпочтительно);
- t-test  только при обоснованной нормальности.

###  Множественные проверки

Одна primary (F1); остальные  guardrail / secondary

## Критерии успеха

Выкат v2 на 100%, если одновременно:

1. F1(B) > F1(A), статистически значимо (α = 0.05);
2. Recall(B) ≥ Recall(A) − δ (например δ = 1 п.п.);
3. `Loss_FN`(B) ≤ `Loss_FN`(A);
4. default rate среди одобренных в B ≤ в A.

Откат на v1, если:

- Recall или `Loss_FN` существенно хуже в B;
- рост FP без выигрыша по одобрениям/риску.

## Guardrails

Остановка эксперимента и откат на v1 (скользящее окно, напр. 24 ч):

| Условие | Порог (пример) |
|---------|----------------|
| Доля 5xx API | > 1% |
| p95 latency | > SLO |
| Recall(B) vs Recall(A) | падение > согласованного δ |
| PSI по ключевым признакам | > 0.2 |
